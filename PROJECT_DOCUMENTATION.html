Overview — what this is & why

A reproducible, transparent pipeline that turns raw weather-archive data into an observed-warming trend chart, with no preprocessed climate datasets in between.

weather-trends answers a single question with full traceability: how much has temperature actually risen over a long observation window, and is that rise statistically significant? It pulls daily mean temperature (temperature_2m_mean) for a globally-distributed set of 12 cities from the free Open-Meteo Archive API, converts each city's yearly average into an anomaly relative to that city's own long-run baseline (so absolute climate differences between, say, Singapore and Moscow cancel out), aggregates those anomalies into a single global yearly series, and fits a linear regression to extract a slope in °C/year along with its p-value and R².

The whole flow is data-driven: there is no hard-coded temperature data anywhere. Numbers come either from the live API or from a deterministic mock generator that synthesizes physically-plausible data (latitude-dependent baseline, hemisphere-correct seasonality, AR(1) weather persistence, and a planted warming trend) so the tool runs and tests pass entirely offline when the API rate-limits.

Key concept
The unit of analysis is the anomaly, not the raw temperature. Each city is mean-centered against its own baseline before aggregation, so the global series measures change, not the meaningless average of 12 unrelated climates.

Current state (Phase 1). A working single-file prototype, weather_trend.py (~407 lines), exists and runs end-to-end. The project is mid-refactor into a typed, tested src/ package. Today, config.py, fetcher.py, mock_data.py, and the four Pydantic models under src/models/ are extracted and tested. The analyzer, visualizer, and cli modules named in the plan (src/analyzer.py, src/visualizer.py, src/cli.py) are not yet created — their logic still lives inside the legacy monolith weather_trend.py.

Watch out
Several docs describe the target design as if it were built. The module names src/analyzer.py, src/visualizer.py, src/cli.py, the tests/conftest.py + tests/test_analyzer.py + tests/test_visualizer.py test files, and a .gitlab-ci.yml pipeline are named in README.md, CLAUDE.md, and docs/WEATHER_TRENDS_MASTER_PLAN.md but do not exist on disk. CI is in fact GitHub Actions (.github/workflows/ci.yml), not GitLab. The Docker CMD runs python -m src.cli, which will fail until that module is written. This guide labels every such gap explicitly and references only files that actually exist.

Architecture

A linear batch pipeline: a data source (live or mock) emits one canonical DataFrame, an analyzer reduces it to a yearly anomaly series plus a trend stat, and a visualizer turns those into PNGs.

There are no long-running processes, no servers, and no persistence in Phase 1. The target design has the program run, write charts to an output/ directory (created at runtime, gitignored — see the OUTPUT_DIR constant in src/config.py:19), and exit. Today the working prototype weather_trend.py instead opens an interactive window via plt.show(). The single most important architectural invariant is the DataFrame contract: every source (fetcher, mock generator, and — in Phase 3 — a database query) produces the exact same five columns, so the analyzer is source-agnostic.

Where things actually live today. The boxes labelled TrendAnalyzer, TrendVisualizer, and CLI entrypoint are the planned module split. In the current tree their behavior is implemented inside weather_trend.py as the methods visualize_weather_data() (anomaly + regression + plot, combined), generate_summary_report() (text summary + decade averages), and run_analysis() (orchestration).

Weather data fetcher src/fetcher.py

WeatherDataFetcher wraps an injectable httpx.Client. fetch_location() issues a GET per city, then dispatches on status: 200 → parse to DataFrame; a response body containing a rate-limit marker → raise RateLimitExceededError immediately (no point retrying); any other non-200 → sleep and retry up to MAX_RETRIES. If all attempts fail it raises WeatherFetchError. fetch_all() maps over locations and pd.concats the frames.

The sleep callable is injected (defaults to time.sleep) so tests pass a no-op and run instantly. _owns_client tracks whether the fetcher created the client; close() only closes clients it owns, never an externally-supplied one.

src/fetcher.py:20RATE_LIMIT_MARKERS — the two Open-Meteo limit strings.
src/fetcher.py:26RateLimitExceededError / WeatherFetchError custom exceptions.
src/fetcher.py:50fetch_location() — the retry/dispatch core.
src/fetcher.py:96_payload_to_dataframe() — adds location/lat/lon columns; raises if daily block missing.
Watch out
The legacy prototype recurses on transient errors (weather_trend.py:66) — an unbounded retry the refactor deliberately replaced with a bounded loop. Do not reintroduce recursion.
Mock data generator src/mock_data.py

MockDataGenerator synthesizes deterministic, physically-plausible temperatures so the tool (and the entire test suite) runs offline. For each location it builds a daily series from four additive components:

  1. Latitude baseline: base_mean = 28 - 0.45·|lat| — ~28 °C at the equator, ~0 °C near 62°.
  2. Seasonality: amplitude grows with latitude (3 + 0.22·|lat|); a cosine peaks mid-year in the northern hemisphere and flips sign in the southern.
  3. AR(1) weather noise: ar[i] = phi·ar[i-1] + eps[i] for day-to-day persistence.
  4. Linear warming trend: trend_c_per_year · (frac_year - year0) plus a small per-location residual.
Key concept
The cosine form is load-bearing. The v0.1.1 fix replaced a sin(2π·doy/365.25) term (which peaked in April and correlated with frac_year, biasing the recovered slope to ~half its planted value) with -hemisphere_sign·cos(...). Cosine over a full year is orthogonal to the linear time axis, so a regression recovers the planted trend cleanly. See docs/versions.md.

Key logic & formulas

The analytical core: anomaly computation, cross-location aggregation with confidence intervals, and significance-tested linear regression.

1 · Per-location anomalies

Raw temperatures are first averaged per (year, location). Each city's baseline is its mean across all years; the anomaly is the yearly value minus that baseline. This removes the absolute climate offset so a tropical and a continental city contribute on the same footing.

2 · Yearly aggregation + 95% CI

Anomalies are aggregated across cities per year into a mean, std, and count, from which standard error and the 95% confidence half-width follow.

mean over cities→std, n→se = std/√n→ci95 = 1.96·se

3 · Trend regression

A linear regression of yearly mean anomaly on year gives the warming rate. The preferred path is scipy.stats.linregress, which returns slope, intercept, R² (=rvalue²), and a two-sided p-value in one call. The legacy file keeps a manual polyfit + Student-t fallback for environments without scipy; the refactor drops the fallback (scipy is a hard dependency).

Key concept
The mock generator and this regression form a closed loop the tests exploit: plant a known slope (e.g. 0.03 °C/yr), generate 30 years of data, regress, and assert the recovered slope matches within atol=0.01 (tests/test_mock_data.py:25). This is the reference-value validation the project mandates.

4 · Decade averages

For the summary, years are floored to decades ((year // 10) * 10) and anomalies averaged per decade — the basis for the planned decade bar chart.

How to run it

Three ways: the launcher scripts (Docker), raw Docker Compose, or local uv. Today the legacy script is the only path that completes end-to-end.

Local (works today)

  1. Install deps: uv sync (resolves from pyproject.toml + uv.lock).
  2. Run the working prototype: uv run python weather_trend.py. It fetches (or falls back to mock) and opens an interactive matplotlib window.
  3. Run tests: uv run pytest --cov=src --cov-report=term-missing.
  4. Lint: uv run ruff check ..

Local (target, once cli.py exists)

  1. uv sync
  2. uv run python -m src.cli — will write PNGs to the runtime-created output/ directory (per src/config.py:19).

Docker

  1. macOS/Linux: ./run_weather_trends.sh · Windows: run_weather_trends.bat.
  2. The launcher runs docker compose up --build -d and drops into a menu loop.
  3. Charts land in the bind-mounted output/ directory on the host (created at runtime; mapped in docker-compose.yml).

How to edit & extend it

Concrete, owner-focused recipes. The dominant near-term task is finishing the refactor; after that, adding cities/charts is trivial.

Finish the refactor (the next real task)
  1. Create a new src/analyzer.py with a TrendAnalyzer that takes the canonical DataFrame and returns a yearly anomaly frame + a TrendResult. Lift the logic from weather_trend.py:209-297; drop the polyfit fallback (scipy is a hard dep).
  2. Create a new src/visualizer.py with a TrendVisualizer that savefigs to config.OUTPUT_DIR at CHART_DPI — never plt.show(). Add the four chart types from CLAUDE.md §9.
  3. Create a new src/cli.py (argparse) orchestrating fetch→analyze→visualize, with a mock fallback on RateLimitExceededError.
  4. Add new tests/test_analyzer.py and tests/test_visualizer.py (use the Agg backend; assert files written). Keep coverage at 100%.
  5. Delete weather_trend.py once parity is confirmed, and remove requests from the environment.
Add or change a city

Edit only src/config.py:23 — append a Location(name=..., lat=..., lon=...). Validation (bounds, names) is automatic via the model. Update tests/test_config.py if you change the count assertion (== 12).

Tip
Coordinates live only here. The data-driven-check skill (.agents/skills/data-driven-check/SKILL.md) will flag any latitude-looking float that creeps into analysis code.
Add a new chart type

Once visualizer.py exists, add a method there and a corresponding test. Keep chart code isolated in the visualizer — never couple analysis to matplotlib. Use seaborn styling (whitegrid/ticks) per the standards, label axes with units, save at CHART_DPI.

Tune the mock generator

All knobs are MockDataGenerator.__init__ args (trend, noise, AR(1) phi, missing rate, seed). Named magnitudes (baseline, amplitude) are constants at the top of src/mock_data.py:10. If you touch the seasonal term, re-run test_hemisphere_seasonality_opposite_phase and test_trend_signal_is_recoverable — both are sensitive to seasonal/time orthogonality.

Key concept
The golden rule for any extension: a new data source must still emit the five-column DataFrame, and any new computed quantity should be expressed as a Pydantic model in its own file under src/models/. One concept per file is enforced project-wide.

How tests mock the API

No network in tests. tests/test_fetcher.py:19 builds the fetcher with an httpx.MockTransport and a no-op sleep, so retries are instant and responses are scripted per request.

Rules (from the validation-protocol skill)

No mocking of math
Never mock linregress, numpy, or pandas aggregations. Only HTTP/filesystem I/O is mocked.
Reference values
At least one test per analysis module compares against an independently known result (e.g. planted slope).
Float comparisons
Always np.testing.assert_allclose with a documented tolerance — never ==.

Full protocol: .agents/skills/validation-protocol/SKILL.md.

Watch out
Coverage source is src/ only (pyproject.toml [tool.coverage.run]); weather_trend.py is excluded, so the legacy file is intentionally untested. Once analyzer/visualizer/cli land, they must hit 100% or CI fails.

Domain glossary

Terms a newcomer needs to read the code and the charts.

Anomaly
A temperature expressed relative to a baseline (here, each city's long-run mean), not an absolute value. The core quantity analyzed.
Baseline
A location's mean temperature across all years; subtracted to form anomalies.
temperature_2m_mean
Open-Meteo's daily mean air temperature at 2 m above ground, in °C — the only variable fetched.
Slope (°C/year)
The warming rate from the linear regression of yearly mean anomaly on year.
p-value
Probability the observed slope arose by chance under a no-trend null; small ⇒ significant warming.
R²
Fraction of year-to-year anomaly variance explained by the linear trend.
CI95 / SE
95% confidence half-width (1.96·SE) and standard error (std/√n) of the cross-city mean anomaly.
AR(1)
First-order autoregression: today's noise depends partly on yesterday's, modeling weather persistence in the mock data.
frac_year
Year plus fractional day-of-year (year + (doy-1)/365.25), the continuous time axis for the planted trend.
Open-Meteo Archive API
Free, key-less historical weather endpoint; the project's sole real data source.
